A GAME MADE OF PIXELS

The games BetVision tests draw their controls and content inside an HTML canvas. A DOM-based tool such as Selenium can find that canvas, but in these games it can't see the controls or the game state drawn inside it.

DOM-BASED TOOL

<canvas>
  • ✓Finds the canvas element
  • ✗Can't inspect the controls drawn inside
  • ✗Can't read the game state drawn inside

VISION AGENT

  • ✓Reads the rendered screen
  • ✓Identifies the game elements
  • ✓Acts in the browser
  • ✓Compares expected with observed
  • ✓Writes a report

Canvas-based games became testable where DOM-based tools such as Selenium couldn't operate. Reusable, parallel test runs cut test cycles from days to hours and manual gameplay validation by over 40%, across 32 markets.

      AUTONOMOUS SOFTWARE
      ENGINEERING PLATFORM

      A multi-agent platform that takes a plain-language requirement through nine engineering stages and produces a working application. I built the proof of concept alone, then led the team that made it a product.

      ROLE
      Architect. Built the proof of concept alone, then led a team.
      GROUP
      Industry Solutions Group, Zensar
      STATUS
      An enterprise product, showcased to clients and adopted internally
      STACK
      Multi-agent LLM architecture, Playwright, OCR

      What it is

      An autonomous multi-agent engineering platform. A user gives it a requirement in plain language. The platform works through the stages of a software project and produces the application: a requirements document, designs, code, a review, tests, validation and a working build.

      It works as a pipeline: each stage takes the previous stage's output as its input.

      The problem

      Software gets built through a chain of hand-offs: from requirement to specification, to design, to code, to review, to tests, to a running build. Each hand-off is a place where meaning can be lost, and each is usually done by a different person at a different time.

      The question behind the platform was whether that whole chain could run from a single requirement.

      The technical challenge

      The hard part is coordination: a requirement has to survive every transformation, and the application at the end has to still be the one the requirement described.

      That is why the later stages examine the running application as well as the code. Review, unit tests, browser tests, screen checks and security testing each look at the result from a different side.

        WORK / MCP SERVER
        MCP SERVER
        A reusable server that lets AI agents reach repositories and engineering tools through one protocol, and pass context from one step to the next.
        ROLE
        Built it
        STACK
        Node.js · TypeScript · MCP · LLM APIs
        OUTPUT
        Structured results with context carried between steps
        FOR
        AI agents working with engineering tools
        

        What it is
        A Model Context Protocol (MCP) server. An AI agent asks for a capability, the server routes the request to the right tool, and the tool's result comes back in a structured form. The server also carries context from one step to the next, so a later step knows what an earlier one found.
        The problem
        An agent can reason, but it needs a way to read a repository or call an engineering tool. Each tool has its own interface, so connecting every agent to every tool means writing glue for each pair.
        Why it is interesting
        The server sits in the middle, so agents and tools can change independently. The hard part is the contract: results have to be structured enough for an agent to read and chain, and context has to move between steps without losing what matters.
